## 実装と検証

`tools/check-site.py` はHTMLのID重複、インラインJavaScript/ES moduleの構文、importmap/JSONを検証する。単一ファイル設計の公開対象は `index.html` と `.nojekyll` のみ。資料、過去版、テスト、`.git`、開発設定を公開しない。HTMLのsrc/poster等から参照するローカル画像・音源・JS等を追加したときは検証で失敗させ、公開manifestを明示的に拡張してからマージする。外部CDNの可用性やゲームルールの正しさを構文検証で保証しない。

PR作成・更新はvalidateのみ。pushイベントも `main` のみ。マージコミットをcheckoutし、検証成功後にその成果物をuploadし、needsでdeployを依存させる。並行実行の取消とdeploy直前のHEAD照合で古いコミットを拒否する。Pages Sourceがworkflowでなければdeployは失敗する。既存のブランチ保護を変更しない。

検証コマンド:

```sh
python3 tools/check-site.py
node tools/share.test.mjs
python3 tools/check-site.py --out _site
```

既存リポジトリに自動テスト定義なし。今回の構文/成果物確認は操作テストを代替しない。

## 適用順（設定が必要）

1. このPRと関連 [実験場PR43](https://github.com/chameleonjp-lab/chameleonjp_lab/pull/43) を確認する。同PRのSQLを適用/読み戻しし `submit_score_once_shared_v1` を先に利用可能にする（現在未適用）。ゲームのマージが先だと名前あり送信は待機になる。GitHub版と旧公開版の操作・ルール差分を確認する。
2. **マージ前に** Settings → Pages → Build and deployment → Source を **GitHub Actions** にする。未設定ならPagesをこの方式で設定する。既存legacy公開のままマージするとGitHub側の従来配信が検証を迂回し得るため、この設定は必須。`github-pages` environmentで既存の承認・ブランチ制限を維持し、公開ブランチ `main` を許可する。
3. 利用者がPRをマージする。validate → deployが同じマージSHAで成功することをActionsとPages deploymentで確認する。
4. Pagesが返した実URLでホーム→開始→正常終了/失敗→結果、モード、ランキング、共有、保存設定を確認する。iPhone Safari実機では縦横、キーボード、戻る、再挑戦、共有からの復帰も確認する。
5. 新URLと機能を確認してから、正式URL/メタ情報の変更PRと実験場の `games.game_url` / `share_text` 更新を行う。DB更新は旧値を保存し対象slug・旧URL条件をつけ、更新後にSELECTで読み戻す。現在この段階は未適用。旧ページ案内はその後に行い、確認前の強制転送はしない。

## 記録とロールバック

スコア保存先、game_slug、mode、score_order=`asc`、scale=`100`、decimals=`2`、採点処理、既存保存キーは変更しない。本番への検証スコア送信は行わない。

CodebergとGitHub Pagesは別originのため、localStorageの名前・自己ベスト・音量・言語は自動では移らない。旧データを残す。移行前に各ゲームの保存キーを列挙し、ゲーム限定のエクスポート/インポートまたはユーザー操作による再設定を設計・検証する必要がある。本人のサーバー記録の帰属は、既存name-key方式の制約と分けて扱う。「すべて引継ぎ済み」とはしない。

公開に不具合があれば直前の安全な変更をrevertするPRをマージし、そのコミットを同じ検証・公開経路で配信する。失敗したbuild/deployでは成功済みの配信を置換しない。実験場はまだ旧URLなので今回の段階では切戻し不要。URL切替後の切戻しは保存した旧DB値を対象slug・現在URL条件付きで復元し、SELECTで確認する。端末保存情報を削除しない。
